Loop Engineering

The programmer's job is shifting from writing the final answer to designing the loop that can reach the answer.

A useful agent should not be expected to one-shot meaningful work. Humans do not work that way. We try something, inspect the result, compare it to the goal, adjust, and repeat. The loop is not a workaround for weak intelligence. It is how intelligent work usually happens.

LLMs are trained on human work: drafts, fixes, tests, explanations, reviews, revisions, and traces of trial and improvement. It should not surprise us that they perform better when we give them the same structure. Goals, tools, feedback, tests, memory, and permission to revise are not optional extras. They are the operating conditions.

The prompt is too small

A prompt can describe intent, but it cannot carry the whole environment. Real work depends on state: the codebase, the failing test, the screenshot, the logs, the hardware response, the user's reaction, and the difference between what happened and what should have happened.

The loop gives the agent a way to keep updating its understanding. Run the thing. Observe the result. Compare it to the goal. Decide what to change. Try again. That is closer to engineering than asking for a perfect answer up front.

The system around the model matters

Loop engineering means building the conditions where the agent can make progress without pretending it already knows everything. The important pieces are ordinary: clear success criteria, runnable checks, observable state, bounded tools, and a record of what changed.

Tests are one form of feedback. Browser screenshots are another. Hardware probes, logs, type errors, user review, and deployment checks all serve the same role. They let the system learn from contact with reality.

The human becomes the loop designer

This does not remove the programmer. It changes the programmer's leverage. Instead of only writing every line, the programmer defines the goal, creates the checks, chooses the tools, constrains the blast radius, and decides when the result is good enough.

The skill is knowing what feedback the agent needs next. Sometimes that is a unit test. Sometimes it is a screenshot. Sometimes it is a subagent looking at a separate part of the system. Sometimes it is stopping and writing a plan so the next pass has a better map.

Stop asking agents to one-shot

The one-shot expectation is a bad interface. It asks the model to compress exploration, execution, verification, and judgment into a single response. That can work for small tasks, but it breaks down exactly where software becomes interesting.

Better agent systems make iteration cheap. They give the agent enough context to act, enough feedback to notice when it is wrong, and enough structure to recover. The future of programming is not just better prompts. It is better loops.
